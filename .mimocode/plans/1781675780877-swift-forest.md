**Goal:** Find vulnerabilities, unsafe patterns, secrets exposure, injection risks, and dependency risks.

### T1.1: Download & Integrity (`src/core/download.rs`, `src/core/integrity.rs`)

**Files:** `src/core/download.rs` (308 lines), `src/core/integrity.rs` (491 lines)

**Checklist:**
1. **SHA-256 checksum validation** — ✅ FIXED: constant-time comparison added
2. **TOCTOU race conditions** — Review: Cached archives ARE verified (false alarm). Windows rename not atomic but acceptable for CLI.
3. **HTTP client configuration** — Review: TLS config well-designed (rustls + native roots). No cert pinning — acceptable. Timeouts appropriate.
4. **Temp file handling** — Review: .partial sibling pattern self-healing. Stale partials overwritten on next run.
5. **Cached archive reuse** — Review: Archives ARE re-verified against live SHASUMS256.txt every time. No vulnerability.
6. **Retry logic** — Review: String-matching fragility is pragmatic tradeoff. 3-attempt limit bounds damage.

**Status:** 1 fix applied, 5 items reviewed and acceptable.

**Checklist:**
1. **Command injection via project names/paths** — ✅ FIXED: shell escaping added
2. **Environment variable escaping** — Review: POSIX single-quote escaping complete. PowerShell escaping has theoretical `%{}` gap but acceptable.
3. **Hook idempotency** — Review: HOOK_MARKER sentinel well-designed. Parallel runs benign.

## Phase 3: Architecture Review ✅ COMPLETE (Observational)

**Goal:** Assess module organization, trait design, separation of concerns, and scalability.

**Key findings documented:** Plugin trait is minimal but adequate, intelligence engine is npm-only, drift detection covers 2 of 8 runtimes, SQLite store has no cache eviction. No code changes needed — these are architectural observations for future improvement.

### 3.1 Plugin Architecture (`src/plugins/`)

**Findings:**
- `LanguagePlugin` trait has 5 methods (name, install_version, list_installed, bin_path, latest_version) — adequate for current use but missing uninstall, async, error types
- `PluginRegistry` is clean (`HashMap<String, Box<dyn LanguagePlugin>>`) — dynamic dispatch is fine for this call frequency
- All 8 plugins are structurally identical — good consistency
- Node plugin uses blocking HTTP while intelligence uses async — inconsistency
- No plugin exposes version metadata (release date, changelog)

### 3.2 Intelligence Engine (`src/intelligence/`)

**Findings:**
- `DependencyRuntimeAdapter` trait is well-scoped but npm-only (7 runtimes use GenericStubAdapter)
- `NpmGraphBuilder` has good multi-version diamond dependency handling
- `IntelGraph` edges use string-based `"name@version"` — requires `rsplit_once('@')` parsing everywhere
- SQLite store has no cache eviction — tables grow unbounded
- `adapter_from_ven_config` is O(n²) if-chain — maintenance hazard
- Drift detection only works for npm and Python — 6 runtimes unsupported

### 3.3 CLI Layer (`src/cli/`)

**Findings:**
- Clean `cmd_verb` naming convention
- `cmd_add` is 485 lines — needs splitting
- No shared state between commands (each creates its own adapter)
- Output formatting inconsistent (some use colored, some plain)

### 3.4 Core Business Logic (`src/core/`)

**Findings:**
- Module cohesion is good — each module does one thing
- No circular dependencies detected
- Configuration propagation: global config → env vars → local ven.toml — correct precedence
- 8 installer modules duplicate same patterns (addressed in Phase 2 with BaseInstaller)

### 3.5 Binary Separation

**Findings:**
- Clean boundaries: `ven` (CLI), `ven-launcher` (portable), `ven-setup` (installer)
- `lib.rs` correctly re-exports for library usage
- Build-time binary embedding via `build.rs` — now with integrity verification (Phase 1)
