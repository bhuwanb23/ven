## BUGS FOUND

### BUG #1 — CRITICAL: `ven lock` completely broken

**Command**: `ven lock`
**Reproduction**: Run `ven lock` in any node/bun project with packages
**Expected**: Generates ven.lock with integrity hashes
**Actual**: Fails with `root 'express' missing from packages map` — every package reported as missing

**Root cause** (`src/intelligence/ven_lock.rs` + `src/cli/lockfile.rs`):
- `cmd_lock` builds roots as bare names (`["express"]`)
- `from_merged_simulations` stores roots as-is but packages map uses composite keys (`"express@5.2.1"`)
- `validate_lock_graph` looks up `packages["express"]` → not found (key is `"express@5.2.1"`)
- Same mismatch for edges: split `"express@5.2.1"` → bare `"express"` → lookup fails

**Fix**:
1. `src/cli/lockfile.rs`: Build roots as `"name@version"` composite keys from resolved graph
2. `src/intelligence/ven_lock.rs` `validate_lock_graph`: Use `edge.from`/`edge.to` directly (already composite) instead of splitting to bare names

### BUG #2 — HIGH: `ven status` lies about installed runtimes

**Command**: `ven status` (non-verbose)
**Reproduction**: Set `node = "22.22.2"` in ven.toml when only 26.3.0 is installed
**Expected**: Warning that 22.22.2 is not installed
**Actual**: Shows `✓ node 22.22.2 (22.22.2)` — green checkmark for missing runtime

**Affected languages** (all 8):
- node: declares 22.22.2, only 26.3.0 on disk → ✓
- python: declares 3.13.12, only 3.11.0/3.12.8 on disk → ✓
- go: declares 1.26.2, only 1.26.4 on disk → ✓
- rust: declares 1.75.0, directory doesn't exist → ✓

**Root cause** (`src/core/config.rs` lines 121-380):
All 8 `resolve_*_version` functions have identical bug. The `_ =>` catch-all arm:
```rust
_ => Ok(spec.to_string()),  // Always returns Ok, never checks installed list
```
For exact version strings (anything with a dot), it unconditionally returns success.

**Fix**: Change `_ =>` arm in all 8 resolve functions to verify the version exists in the installed list before returning `Ok`.

### BUG #3 — MEDIUM: `ven check` contradictory output

**Command**: `ven check`
**Reproduction**: Run in node project with node 22.22.2 declared
**Expected**: Either flag as actionable or don't mention it
**Actual**:
```
[SUPPORT-ENDED] nodejs 22.22.2 (cycle 22)
    ...
[OK] No actionable issues.   ← contradicts the above
```

**Root cause**: The check command considers "support ended" but not "past EOL" as actionable. The logic distinguishes between "support ended" (non-actionable) and "EOL" (actionable), but the UX is confusing — users see a warning and then "no issues".

**Fix**: Either make "support ended" actionable, or don't display it as a warning.

---

### BUG #4 — MEDIUM: `ven resolve` not usable non-interactively

**Command**: `ven resolve`
**Reproduction**: Run `ven resolve` in a project with conflicts
**Expected**: `--yes` or `--force` flag to skip prompt
**Actual**: Hangs at `Apply? [y/N]:` with no way to auto-apply

**Impact**: Cannot use in CI/CD or scripts.

**Fix**: Add `--yes`/`--force` flag that auto-applies the resolution.

### BUG #5 — LOW: `ven install` doesn't validate version upfront

**Command**: `ven install node 99.99.99`
**Reproduction**: Install a nonexistent version
**Expected**: Early validation error: "Version 99.99.99 not available"
**Actual**: Says `[OK] Resolved to node 99.99.99`, starts download, then fails with HTTP 404

**Fix**: Validate version exists in registry before attempting download.
