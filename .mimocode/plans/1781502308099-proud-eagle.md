# Plan: Core Rust CLI Architecture - "ven"

## Executive Summary

**ven** is an intelligent, multi-language version and dependency manager written in Rust. This document provides a comprehensive understanding of the core CLI architecture, plugin system, and intelligence engine.

## 1. CLI Layer (`src/cli/`)

### Command Definition & Dispatch

- **Entry**: `src/main.rs` (7 lines) → `Cli::parse()` → `run()`
- **CLI Definition**: `src/cli/mod.rs` (831 lines) with clap derive macros
- **Dispatch**: Single giant `match` statement (lines 688-816)

```rust
pub fn run(cli: Cli) -> Result<()> {
    match cli.command {
        Commands::Install { language, version } => { /* 4-arm match */ }
        Commands::Add { packages, skip_check, dry_run, verbose, yes } => add::cmd_add(...),
        Commands::Remove { ... } => remove::cmd_remove(...),
        // ... 20+ more arms
    }
}
```

### Error Handling Patterns

1. **Early return with `anyhow::bail!`** (CI-safe exit codes)
2. **`Result<T>` propagation with `?`** (standard Rust)
3. **Soft failures with colored output + `continue`** (batch operations)
4. **Security scan wrapped in `block_on` with fallback**

### Cross-Cutting Patterns

- **Dual output mode**: `--json` flag for machine-readable output
- **Dry-run pattern**: `--dry-run` runs analysis but skips mutation
- **Interactive confirmation**: `--yes` flag + `stdin_is_interactive()` check
- **TOML surgery**: `toml_edit::DocumentMut` for preserving comments/formatting

## 2. Plugin System (`src/plugins/`)

### LanguagePlugin Trait

```rust
pub trait LanguagePlugin: Send + Sync {
    fn name(&self) -> &str;
    fn install_version(&self, version: &str) -> Result<()>;
    fn list_installed(&self) -> Result<Vec<String>>;
    fn bin_path(&self, version: &str) -> Result<PathBuf>;
    fn latest_version(&self) -> Result<String>;
}
```

### Plugin Registry

```rust
pub struct PluginRegistry {
    plugins: HashMap<String, Box<dyn LanguagePlugin>>,
}
```

- **Static registration** (no dynamic loading)
- 8 plugins: Node, Python, Go, Rust, Bun, Deno, Java, Ruby
- Used for **runtime management** (install, list, delete, path)

### Plugin Implementation Pattern

All plugins follow identical structure:
```rust
pub struct XxxPlugin;

impl LanguagePlugin for XxxPlugin {
    fn install_version(&self, version: &str) -> Result<()> {
        let downloader = XxxDownloader::new()?;
        install_xxx(&downloader, version)
    }
    // ... delegate to core::xxx_install module
}
```

## 3. Intelligence Engine (`src/intelligence/`)

### Core Data Model

**`IntelGraph`** - Multi-version dependency graph:
```rust
pub struct IntelGraph {
    pub runtime_kind: RuntimeKind,
    pub runtime_version: String,
    pub nodes: BTreeMap<String, BTreeMap<semver::Version, IntelNode>>,
    pub edges: Vec<IntelEdge>,
}
```

**Critical design**: Multi-version node storage enables diamond dependency detection.

**`SimulationResult`** - Output of pre-flight analysis:
```rust
pub struct SimulationResult {
    pub compatible: bool,
    pub graph: IntelGraph,
    pub conflict_chains: Vec<ConflictChain>,
    pub engine_incompatibilities: Vec<EngineIncompatibility>,
    pub suggestions: Vec<ResolutionOption>,
    pub warnings: Vec<String>,
}
```

### Adapter Layer

**`DependencyRuntimeAdapter`** trait:
```rust
#[async_trait(?Send)]
pub trait DependencyRuntimeAdapter {
    fn runtime_kind(&self) -> RuntimeKind;
    fn runtime_version(&self) -> &str;
    async fn simulate_add(...) -> Result<SimulationResult>;
    async fn simulate_upgrade(...) -> Result<SimulationResult>;
    async fn current_environment_graph(...) -> Result<IntelGraph>;
    async fn check_add(...) -> Result<CheckAddResult>;
}
```

**Two adapter implementations**:
1. **`NpmFamilyAdapter`** - Full-featured for Node/Bun
2. **`GenericStubAdapter`** - Stub for Python, Go, Rust, Java, Deno, Ruby

### NpmGraphBuilder (`intelligence/adapters/npm.rs`)

Recursive dependency tree walker:
- Depth limit of 20
- Diamond dependency handling (same name, different version → separate entries)
- Peer dependency resolution in second pass
- Version resolution (semver ranges, latest, lts, exact)

### Conflict Detection (`intelligence/conflicts.rs`)

Three conflict categories:
1. **Peer dependency violations**
2. **Diamond dependency conflicts**
3. **ven.toml pin mismatches**

### Persistence Layer (`intelligence/store.rs`)

SQLite-backed cache at `~/.ven/intelligence.db`:
- `snapshots` - Full SimulationResult as JSON
- `package_cache` - Per-package metadata
- `dependency_cache` - Per-edge relationships
- `lock_validations` - Lockfile integrity checks

## 4. Core Business Logic (`src/core/`)

### Configuration Management

**Two-tier config**:
1. **Per-project** (`ven.toml`): `VenConfig` with runtime, packages, env sections
2. **Per-user** (`~/.config/ven/config.toml`): Global config pointer

**Config discovery**: `find_ven_toml()` walks up directory tree (like `.gitignore`)

### Storage Root Resolution (`ven_home.rs`)

5-level priority:
1. `$VEN_HOME` env var
2. `$VEN_STORAGE_PATH` env var
3. Portable mode (`<exe-dir>/.ven`)
4. Pointer file (`~/.config/ven/config.toml`)
5. Default `~/.ven`

### HTTP + SQLite Caching Pattern

Four caches with consistent architecture:
| Cache | TTL | Purpose |
|-------|-----|---------|
| Registry | 24h | npm package metadata |
| OSV | 6h | CVE vulnerability data |
| EOL | 24h | Runtime end-of-life dates |
| Docs | 7d | Package documentation |

**Key feature**: Stale-while-revalidate on network failure

### Security Scanning

**Two scanners**:
1. **npm Advisory** (`security.rs`) - npm Bulk Advisory API
2. **OSV** (`osv.rs`) - Multi-ecosystem via osv.dev API (565 lines)

### Ghost Scanner (`ghost_scanner.rs` - 1280 lines)

Detects **undeclared imports** across 7 ecosystems:
- Two-phase algorithm: collect declared deps → walk source and extract imports
- Gitignore-aware directory traversal
- Per-ecosystem regex extraction
- Hardcoded stdlib exclusion lists

### Documentation Fetcher (`doc_fetcher.rs`)

Per-ecosystem doc sources:
- npm → registry.npmjs.org (README from JSON)
- Python → pypi.org (description)
- Ruby → rubygems.org (info)
- Rust/Go/Java/Deno → HTML-only (direct to browser)

## 5. Data Flow: `ven add express`

```
User runs: ven add express
        │
        ▼
cli/add/mod.rs :: cmd_add()
        │
        ├── load_config() → VenConfig (reads ven.toml)
        │     RuntimeConfig { node: "20.11.0", ... }
        │
        ├── Determine runtime mode (node_mode = true)
        │
        ├── load_existing_packages() → HashMap<String, String>
        │     e.g., { "lodash": "^4.17.21" }
        │
        └── For each package:
                │
                ▼
        DependencyIntelligenceService::simulate_add()
                │
                ├── adapter_from_ven_config()
                │     Returns: NpmFamilyAdapter
                │
                └── block_on(async { adapter.simulate_add() })
                        │
                        ▼
                NpmFamilyAdapter::run_simulation()
                        │
                        ├── NpmGraphBuilder::build()
                        │     ├── build_package("express", "latest")
                        │     │     ├── registry.fetch_package_metadata()
                        │     │     ├── resolve_version() → "4.19.2"
                        │     │     ├── add_node()
                        │     │     └── fetch_deps() [recursive, depth ≤ 20]
                        │     └── add_peer_edges()
                        │
                        ├── engine_checks(&graph)
                        │     → Vec<EngineIncompatibility>
                        │
                        ├── analyze_npm_graph(&graph, &existing)
                        │     → (Vec<ConflictChain>, Vec<ResolutionOption>)
                        │
                        └── compatible = conflicts.is_empty()
                                │
                                ▼
                SimulationResult { compatible, graph, conflicts, suggestions }
                │
                ▼
        Back in cmd_add():
                ├── Print dependency tree (if --verbose)
                ├── Print conflict chains
                ├── If !compatible → abort
                ├── persist_snapshot() [SQLite]
                ├── Security scan
                ├── Prompt user
                ├── packages::npm_install()
                └── update_ven_toml_packages()
```

## 7. Architecture Decisions

1. **Two-tier abstraction**: `LanguagePlugin` for runtime management, `DependencyRuntimeAdapter` for dependency analysis
2. **Multi-version node storage**: `BTreeMap<String, BTreeMap<Version, IntelNode>>` enables diamond dependency detection
3. **Graceful degradation**: Non-npm ecosystems get stub adapters (compatible with warnings)
4. **Sync-over-async bridge**: `block_on()` enables sync CLI to call async adapter code
5. **Static plugin registration**: No dynamic loading (trades extensibility for simplicity)
6. **Stale-while-revalidate**: Caches serve stale data on network failure (offline support)

## Summary

This plan provides a comprehensive understanding of the ven project's Core Rust CLI architecture. The project is well-structured with clear separation of concerns:

- **CLI Layer**: Thin orchestration layer with 27+ subcommands
- **Plugin System**: Runtime management for 8 languages via trait abstraction
- **Intelligence Engine**: Predictive dependency analysis with multi-version graph support
- **Core Logic**: Configuration, caching, security scanning, and documentation

The architecture decisions prioritize:
- **Predictive analysis** over reactive installation
- **Diamond dependency detection** via multi-version node storage
- **Offline support** via stale-while-revalidate caching
- **Graceful degradation** for non-npm ecosystems

This understanding should enable effective navigation and contribution to the codebase.
